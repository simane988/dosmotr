# scripts/ — как этим пользоваться

Три скрипта плюс один фильтр. `emulator.sh` — про тесты, остальные три — про то,
чтобы задача из `todo/` доехала до `develop` сама.

| файл | что делает |
| --- | --- |
| `grind.sh` | цикл по бэклогу: выбрать задачу → сделать → ревью → закрыть → следующая |
| `close-task.sh` | закрыть одну задачу: PR, авто-мёрж, перенос файлов в `todo/done/` |
| `claude-stream.py` | делает вывод неинтерактивной сессии читаемым (мысли, вызовы инструментов) |
| `emulator.sh` | локальный AVD `dosmotr_ci_35` для инструментальных тестов |

`emulator.sh test` поднимает эмулятор **в окне, на GPU хоста** — это вдвое быстрее
headless (50s против 116s) и на гигабайт легче. `--headless` — когда нужно
воспроизвести CI; на голом tty или по ssh скрипт переключается туда сам.

Режим, который просят, всегда и получают: уже поднятый эмулятор в том же режиме
переиспользуется, в другом — гасится и стартует заново (`-no-window` на живом не
переключается). Режим определяется по командной строке процесса, а не по файлу
состояния, поэтому эмулятор, запущенный руками, тоже опознаётся верно.

Полное описание механик — в `CLAUDE.md` («Closing a todo task», «Working the whole
backlog»). Здесь — порядок действий.

---

## Быстрый старт

```bash
scripts/grind.sh --once     # одна задача от выбора до мёржа, потом стоп
```

Запускать **из своего терминала**, не из сессии Claude Code: каждая задача — это
отдельный процесс `claude` на переднем плане этого терминала.

Первый прогон лучше делать так: `--once` (одна задача), посмотреть, что получилось,
и только потом отпускать цикл целиком.

---

## Что происходит за один проход

```
выбор задачи  →  автор пишет код  →  PR (без мёржа)  →  ревьюер  →  правки  →  мёрж  →  todo/done/
                 ▲                                        │
                 └──────────── findings ──────────────────┘
```

1. **Выбор.** Один дешёвый вызов `claude -p` без инструментов: ему дают открытые id
   и `todo/README.md`, он отвечает одним id. Повторяется перед каждой задачей — выбор
   учитывает то, что изменила предыдущая. Мусорный ответ → откат на порядок бэклога,
   баги вперёд.
2. **Автор.** Сессия с фиксированным `--session-id`, читает `todo/{bugs,features}/<id>.md`,
   ветвится от `develop`, пишет код, гоняет `testDebugUnitTest` / `lintDebug` / `detekt`,
   коммитит и заканчивает на `close-task.sh <id> --pr-only` — PR открыт, ничего не
   смёржено.
   Перед этим сессия пишет **описание PR по-русски** в `todo/.grind/<id>.pr.md`
   (что было не так, что изменено и почему именно так, что осталось нетронутым,
   как проверено) и передаёт его через `--body-file`. Строку `Closes …` со
   ссылкой на спеку `close-task.sh` дописывает сам.
3. **Ревью.** Каждый раунд — **новая** сессия с read-only инструментами: читает
   `git diff origin/develop...HEAD` против спеки и инвариантов из `CLAUDE.md`, отвечает
   `VERDICT: APPROVE` или `VERDICT: REQUEST_CHANGES`. Отчёты лежат в
   `todo/.grind/<id>.review.<n>.md`.
4. **Правки.** Findings отправляются **в ту же** авторскую сессию — она чинит с полным
   контекстом того, как писала код. Следующий раунд — снова свежий ревьюер, и ему дают
   предыдущий отчёт, чтобы проверил каждый пункт.
5. **Закрытие.** После approve — `close-task.sh <id>`: авто-мёрж, ссылка на PR в файл
   задачи, файлы в `todo/done/`, `todo/README.md` помечен ✅, локально `develop` + `pull`.

По умолчанию три раунда ревью, дальше скрипт спрашивает (`--rounds N`, чтобы поднять).

---

## Флаги `grind.sh`

```bash
scripts/grind.sh                 # спрашивает перед каждой задачей
scripts/grind.sh --yes           # без вопросов, до опустошения бэклога
scripts/grind.sh --once          # ровно одна задача
scripts/grind.sh --task bug-4    # начать с этой, дальше выбирать как обычно
scripts/grind.sh --no-review     # сразу мёрж, без раундов ревью
scripts/grind.sh --rounds 5      # больше раундов, прежде чем сдаться
scripts/grind.sh --mode auto     # останавливаться на рискованных вызовах
scripts/grind.sh --model <name>  # модель для всех сессий
```

Режим по умолчанию — `bypassPermissions`: разрешений не спрашивают вообще. Это и есть
смысл цикла без присмотра, но помнить стоит: такие сессии сами пушат ветки, открывают
PR и взводят авто-мёрж. `--mode acceptEdits` спрашивает про всё, кроме правок файлов.

## Смотреть, но не печатать

Сессии неинтерактивные (`claude -p`) — иначе после выполненной работы `claude` встаёт
у своего промпта и ждёт, а скрипт над ним висит до Ctrl-C, и ни ревью, ни мёржа не
будет. Поэтому:

- в терминале видно всё — мысли, вызовы инструментов, их результаты, итог по стоимости;
  это рендерит `claude-stream.py`;
- **вводить туда ничего нельзя** — сессия не читает stdin;
- вопросов сессия не задаёт: в промпте ей сказано решать самой и фиксировать допущение.

Ctrl-C останавливает прогон, но не теряет работу — см. ниже.

## Лимиты, Ctrl-C, закрытый ноутбук

У каждой задачи фиксированный session id в `todo/.grind/<id>.session`. Прогресс
меряется артефактами, а не словами сессии: фаза 1 закрыта, когда `gh pr list` показывает
открытый PR; фаза 3 — когда появился `todo/done/<id>.md`.

Сессия кончилась, а PR нет — скрипт предлагает:

```
[r]esume  [w]ait 1h then resume  [s]kip  [q]uit
```

`r` продолжает **ту же** переписку со всем контекстом. Под `--yes` скрипт сам ждёт 15
минут и повторяет, до пяти раз, потом пропускает задачу. `s` и `q` печатают команду
`claude --resume <id>` — вернуться можно когда угодно.

## Одна задача вручную

Цикл не обязателен. Если задачу сделали руками на `feature/<name>`:

```bash
scripts/close-task.sh feature-11                       # заголовок PR = subject последнего коммита
scripts/close-task.sh bug-3 --title "fix: …"
scripts/close-task.sh feature-11 --no-wait             # взвести авто-мёрж и не ждать
scripts/close-task.sh feature-11 --pr-only             # только открыть PR
scripts/close-task.sh feature-11 --body-file my.md     # описание PR из файла
```

Описание PR — обычный текст на русском: что и зачем. Без `--body-file` в теле
остаётся только ссылка на файл задачи.

Скрипт откажется работать где-либо, кроме ветки `feature/**`, и при грязном дереве.
`--pr-only` — это ровно та половина, которую делает авторская сессия перед ревью;
повторный запуск без флага подхватывает тот же PR и доводит дело до конца.

`todo/` в `.gitignore`, поэтому вся бухгалтерия (ссылка на PR, перенос в `done/`,
галочки в индексе) — локальная: ничего не коммитится и ничего не пушится в `develop`.

## Что должно быть включено на GitHub

- **Allow auto-merge** в настройках репозитория — без этого `close-task.sh` оставит PR
  открытым, а не смёржит его другим способом.
- Защита `develop` со всеми семью проверками CI (описана в `CLAUDE.md`). Если PR
  сливается мгновенно — проверить в первую очередь именно её.

## Когда что-то пошло не так

| симптом | причина |
| --- | --- |
| PR слился, не дождавшись CI | на `develop` нет защиты ветки / не требуются проверки |
| PR висит, проверок ноль | у head-коммита маркер пропуска CI; `close-task.sh` толкает пустой коммит сам |
| красный чек на ветке после мёржа | `--delete-branch` убрал ветку, `actions/checkout` упал — это бухгалтерия, а не сломанная сборка; вердикт — прогон на `develop` |
| `Input must be provided either through stdin or as a prompt argument` | промпт стоит после `--tools`: флаг вариадический и съедает его. `claude_run` подаёт промпт в stdin именно поэтому |
| `the reviewer produced nothing` | ревьюер не отработал (лимит, сбой) — это не approve, PR остаётся открытым |
| цикл предлагает одну и ту же задачу | она в пропущенных на этот прогон; `--task <id>`, чтобы вернуться к ней |
| скрипт «висит» без вывода | ждёт мёржа; ожидание ограничено часом, потом PR остаётся открытым |

Память машины — отдельная тема: эмулятор (~2.5 ГБ) и Gradle (~2.8 ГБ) рядом с браузером
в 8 ГБ не помещаются, см. «Memory budget» в `CLAUDE.md`.
